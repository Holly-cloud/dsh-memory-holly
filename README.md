# dsh-memory

**一句话**：把「长期记忆」做进 DSH 本身的**原生插件**——记忆存在本机 SQLite 里，宿主半注册 13 个
`memory_*` 工具与一组 `/api/dsh-memory/*` 面板路由，客户端半在左栏放一个「记忆」面板；
检索是「关键词（FTS5 trigram + LIKE 兜底）+ 向量（暴力余弦）」两路并用、按 **RRF 只排名次**融合。

## 当前形态

| 事实 | 说明 |
|---|---|
| **DSH 原生插件** | 宿主半 `lib/index.js` + `src/host/*.js`；客户端半 `lib/client.js`（免构建手写束） |
| **无 Python / 无 mem0 / 无 Chroma / 无 Qdrant / 无 MCP / 无安装器** | 持久化用 Node 24 内置的 `node:sqlite`；没有独立进程，也就没有端口、没有单进程铁律 |
| **零第三方依赖、零裸导入** | 只能 `import 'node:*'` 与包内相对路径。`@deepseek-ai/*` 在磁盘上**不存在**（见 `DESIGN.md` §A），能力全部经 `ctx` 拿 |
| **数据只在本机** | 出网只发生在「嵌入」与「LLM 抽取/冲突判定」两处，取决于 provider 配的是谁；插件自己不埋遥测 |

安装形态、每个文件干什么、跨阶段契约都在 [`DESIGN.md`](DESIGN.md)；Phase 0 的通路实测在 [`PHASE0.md`](PHASE0.md)。

## 安装

不需要 `pnpm`、不需要 `dsh.bundle`、不需要进 `dsh.profile.bundles`。
在 profile 的 patch 文件 `<DSH_HOME>\profiles\desktop\cordis.patch.yml` **末尾**追加：

```yaml
# ── dsh-memory：工作区里的本地记忆插件 ──────────────────────────────
# 卸载 = 删掉这个 insert 块。
- insert:
    - id: memory
      name: '<DSH 工作区>/dsh-memory/lib/index.js'
      config:
        dataDir: '<DSH_HOME>/dsh-memory'
```

改完 patch 文件即热生效（Loader 重放 patch 层），**不需要重启 DSH**。验证：

```powershell
# 1) 行应该在、且 fiberPhase 是 active —— 用 agent 侧 plugin_manager(list_plugins) 看 id=memory
# 2) 无 Cookie 直接打面板路由：应该 401（说明路由已注册、且信任栅栏生效）
Invoke-WebRequest -SkipHttpErrorCheck 'http://127.0.0.1:19387/api/dsh-memory/state'
# 3) 左栏应出现「记忆」图标，点开是四个入口（仓管 / 副仓管 / 搜索 / 设置）
```

### 为什么行名写**绝对路径**，而不是包名

`insert` 行里的 `name` 若是绝对路径，patch 加载器会把它转成
`file:///<DSH 工作区>/dsh-memory/lib/index.js`
再加载——于是**绕开了 Node 的包解析**，也就不需要 `node_modules` 里有这个包。

### 为什么不用 pnpm 安装

`dsh plugin --profile desktop add` 在 desktop 上走 `runProfilePnpm`（`pnpm add` + 版本闸门），
而本机 npm 源不可达；Plugins 页的 bundle 安装又以 `not-bundle` 拒绝没有 `dsh.bundle` 的包。
真正能生效的只有上面这个 patch 块。备份留在 `<DSH 工作区>/dsh-memory-data/.install/cordis.patch.yml.bak`（机器配置，随私人数据一起搁在仓库外）。

### 开发期再加一段（可选）

要让 `lib/*.js` 改了约 9 秒热重载（否则每次改宿主半都要重启 DSH）：

```yaml
- id: hmr
  config:
    base: 'file:///<DSH 工作区>/dsh-memory/'
    root: ['.']
```

两个字段都**必须**这样写：`base` 会被当作 URL 解析（写 `C:/...` 会被当成 scheme `c:` 直接炸），
`root` 是**相对 `base`** 的（写成 profile 之外的绝对路径会让相对路径变成 `../../..`，
正好被默认 ignored 的 `**/.*` 吃掉，watcher 静默失效）。原因见 `PHASE0.md` §6。

## 数据

| 项 | 值 |
|---|---|
| 库文件 | `<dataDir>/memory.db`；`dataDir` 默认 `$DSH_HOME/dsh-memory`（本机即 `<DSH_HOME>/dsh-memory/memory.db`） |
| 打开方式 | `PRAGMA busy_timeout=5000`、`foreign_keys=ON`、非内存库启用 `journal_mode=WAL` |
| 表 | `schema_meta` / `memories` / `memories_fts` / `vectors`（主键 `memory_id + space`）/ `spaces` / `history` / `batches` / `batch_items` / `palace_sources`（来源账本，见下）/ `jobs` / `settings` / `keeper_plans`（变更单）/ `keeper_handoffs`（**副审阅区**，原「待接手记忆」） |

> `palace_sources` 是「某个源文件灌了多少块」的账本表（`upsertSource` / `getSource` / `listSources` 三个方法都在）。
> 原「宫殿同步」功能已于 2026-10-06 退役（归档在 `<DSH 工作区>/dsh-memory-data/.retired/palace/`），**当前没有功能写它**；
> 表与方法保留，免得 schema 与代码更不一致。

**文本是本体，向量是派生物**：

- `memories.text` 是唯一真相；`vectors` 里只有 `Float32Array` 的 BLOB，**任何一套都可以整表删掉重算**，一条记忆都不会丢；
- **向量按「空间」保留，换模型不再重算全库**：`space` 是 `provider:model:dims` 指纹，
  同一条记忆可以同时存好几套向量。换模型 = 新建一个空间（旧空间一行都不动），
  切回来**只补「离开期间新增的」那几条**（`memory_stats` 的 `activeSpace.missing` 会显示 `缺 N 条`）；
- 检索只在**当前配置算出的**那个空间里做：那个空间还没补齐时明确回「需补齐」并降级为关键词，
  **绝不拿别的模型算的向量硬凑**；
- 包（导出）里**没有向量**——导入时用目标机器当前的模型重算（见下文「导出 / 导入」）。

> **老库自动升级**：schema v1（一条记忆只能有一套向量）在首次打开时原地升级到 v2，
> 老表改名成 `vectors_v1` 留底（可手动 `DROP TABLE vectors_v1` 回收空间），
> 记忆与向量条数不变，升级结果会写在日志与 `memory_stats` 里。

**回滚靠 `history` 表**：`add` / `supersede` / `delete` / `hard_delete` 四种操作都会写一行
（`prev_text` / `next_text` / `at` / `note`）。`memory_forget` 是**软删**（只填 `deleted_at`，
行与历史都在），`hard_delete` 真删行但历史仍留。回滚 = 从 `history.prev_text` 取回原文再写回去；
**没有一键回滚按钮**，历史是审计与手工恢复的依据。

## 上传 / 版本管理（仓库与数据的边界）

**铁律：记忆数据永不入库。** 本仓库只放代码、文档与 `lib/` 构建产物（连同本 README 在内约 52 个文件 / 1.8 MB）；
记忆数据（`memory.db`、`memories.jsonl`、导出包、退役快照）住在仓库**外**的
`<DSH 工作区>/dsh-memory-data/`，`.gitignore` 里也写死了这些名字（`.migration/` / `.import/` /
`.retired/` / `.install/` / `*.db` / `*.jsonl`）。

> ⚠️ 克隆回来能**跑插件**，但**没有记忆** —— 记忆靠 `memory_import` 从导出包恢复（见上面「导出 / 导入」）。

**推送到 GitHub（本机实测口径）**：本机 git 默认的 `schannel` TLS 后端**发不出去**
（`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`，走不走代理都一样），
换 **openssl** 后端即通：

```powershell
# 1) 干净 remote（不含凭据）
git remote add origin https://github.com/<你的账号>/<仓库>.git
# 2) 推送时临时喂 token，且指定 openssl 后端 —— token 不落 .git/config、不进凭据管理器
$env:GIT_TERMINAL_PROMPT = '0'
$env:GH_TOKEN = '<你的 PAT>'
git -c http.sslBackend=openssl -c credential.helper= push `
  "https://x-access-token:$env:GH_TOKEN@github.com/<你的账号>/<仓库>.git" main:main
Remove-Item Env:GH_TOKEN
```

- 只要照抄 `-c http.sslBackend=openssl` 这一项即可；**不要**把 token 写进 remote URL 后 `git remote add`，
  否则它会留在 `.git/config` 里。
- 细粒度 PAT（`github_pat_…`）只支持 HTTPS，**不能走 SSH**。

## 工具（15 个）

| 工具 | 什么时候用 |
|---|---|
| `memory_search` | 用户说「你还记得吗」「上次」「之前说过」，或你要做决定而不确定细节时。返回按相关度排序；score 只是线索，关键那条未必排第一，**换个说法再查一次常常有效**。命中即给每条 `readScore`（读取指数）+1（**面板浏览 / 仓管内部召回不算**） |
| `memory_remember` | 用户明确要求记住的长期有效事实（偏好、约定、身份、决定、经历）。**原文直存、秒级、不过 LLM**，是日常默认 |
| `memory_extract` | 内容很长（会议记录 / 日记 / 文章），想让模型自己拆成一条条事实。**只落待审区、不进库** |
| `memory_pending` | 看有哪些待审批次（抽取式写入的缓冲区） |
| `memory_analyze` | 批准前逐条查冲突：每条新事实与库里相似记忆是 supersede / duplicate / coexist / unrelated |
| `memory_review` | 批准一个批次（`keep` 是 0-based 白名单、`edits` 改文本、`actions.supersede` 才改写旧记忆）；`reject` 只关批次、不删数据 |
| `memory_list` | 翻旧账：按时间倒序列出，支持分页 |
| `memory_get` | 取一条记忆的**完整原文**（返回值里带 `readScore` / `tidyScore`；取单条也会让读取指数 +1） |
| `memory_forget` | 删一条：默认**软删**（可恢复）；`hard: true` 才真删行（不可恢复，但 `history` 仍留有 prev_text） |
| `memory_stats` | 条数（含 scope 分布）、已保留的向量空间、当前空间还缺多少、待审数、能力自描述、**`scores`（读取 / 整理的总分与均值、Top-N、每周衰减参数与下次衰减时间）**。`probe: true` 时顺带**预检 LLM**（真调一次）。读取侧注入的现状也在这一格里：`recall.feed`（喂入台账）+ `recall.engine`（本轮索引/召回命中），见「读取侧注入」节 |
| `memory_embedding` | 查看 / 测试 / 切换嵌入配置档案：`action=list` 看每个档案的空间与缺口，`action=test` 真打一次请求核对维度，`action=activate` 切换（**保留旧空间向量**，`autoFill: true` 顺手补齐缺的）。新建档案与写密钥在面板「设置」里 |
| `memory_backup` | **一键备份**：库本体（SQLite `VACUUM INTO` 在线快照）+ 可读文本包，写进 `<dataDir>/备份/backup-<时间戳>/`，只保留最近几份 |
| `memory_keeper` | **仓管**：用插件**自带的本地/局域网 LLM**（`keeper.*`，与宿主模型无关）对已录入的记忆做全库二次加工。⚠️ **范式（2026-10-07 起）：仓管只出「变更单」，不改库** —— `action=run` 跑一轮只往 `keeper_plans` 表写单（随机抽 `sample` 个种子 → 每个种子用 embedding 语义召回 `perGroup` 个邻居成组 → 每组一次调用出一张单；`maxGroups` 可限组数），**记忆正文一个字符都不动**；`action=plans` / `plan` 看单（`state` 可筛 open/approved/rejected/partial）；`action=review` 由人（或 agent）**审过才落库** —— `id` 必填、`keep` 勾选要应用的 op 下标（省略 = 全部）、`edits` 就地手改正文（**split 给字符串数组、replace / merge 给字符串**，drop 忽略；不传 = 用仓管给的 `after`；类型不合当场报错）、`reject:true` 整单驳回不碰库；**`reviewKeeperPlan` 是唯一落库入口**。`action=propose` 是**手工提出修改**的入口（`id` + `text` = 修改后的新正文，可选 `reason`）：校验 id 存在未删、text 非空且与原文不同 → 建一张单 op 的 `replace` 单（**只出单、不落库**）。`action=propose-drop` 是**手工提出删除**的入口（`id`，可选 `reason`）：校验 id 存在未删 → 建一张单 op 的 `drop` 单（**只出单、不落库**），过审后该条**软删**（可恢复）、`revert` 能放回来 —— 删改都只能走待审区（⚠️ **删除必须先说服人**：`drop` op 的 `reason` 为空时照旧出单、但 `review` **无论如何都不应用它**，返回里的 `noReason` 是跳过条数；`propose-drop` 自己带默认理由「手工提出的删除」）。`action=handoffs` 列出**副仓管**（原「副审阅区」/「待接手记忆」：仓管某一组出错、又没被接手模型救回来的组，加上被人**转手**过来的单），`action=takeover`（`id`，`model` 可选）让接手模型**重头**再做一遍（拿这一行的成员当种子、**用 embedding 召回相关记忆** → 组 → 出单）—— **省略 `model` 就用副仓管这个角色的设定**，`action=side`（`model` = 档案名 / `'host'` / `'auto'`）**设定副仓管这个独立角色用哪个模型**（存 `settings.keeper.side`，与主仓管的 `keeper.active` 各存各的；改完之后 `takeover` / `run` 省略 `model`（`taker`）时都走它）、`action=handoff`（`id`，`reason` 可选）**把一张待审变更单转手给副仓管重头做**（原单停在终态 `handed`）、`action=drop-handoff`（`id`）把它从队列里清掉（软状态 `dropped`，不删行）—— 这些动作与面板走**同一批** service 方法。**统一修改语义（用户 2026-10-07 拍板）**：修改记忆 = 依照原记忆编写修改后的记忆 → 新旧记忆展示在待审区 → 过审后**删除原记忆、录入新记忆**（原条软删=可恢复、新条新 id 并记 `meta.replaces`）—— 所以修改类 op 只有 `replace`（旧 `rewrite` 一律按它处理），**没有「原地改写同一条」这条路径**。`action=grind` / `digest` 保留名字，**现在都只是 `run` 的别名**（只出单）；`action=revert` 回滚：删研磨产物、按 history 恢复历史遗留的直改痕迹、放回 `merge` 软删的其余条（凭保留条的 `meta.merged`）、**把 `replace` 的新记忆真删、原记忆放回来**（凭新条的 `meta.replaces`），以及**放回 `drop` 软删的条**（从已应用变更单的 `drop` op 取 `targets`）。档案：`action=profiles` / `save` / `delete` / `activate`（线上 OpenAI 兼容 / 局域网 / 本机，可主动切换、**立刻生效**）；`action=status` 看配置/指向/进度/待审单数，`action=test` 真打一次请求验连通性（可带 `name` = 只测那个档案、不切换） |
| `memory_export` | 换机器 / 备份 / 给人看：导出成包（`manifest.json` + `memories.jsonl` + `readable.md` + `RESTORE.md`）；省略 `scope` = 只导配置里的默认 scope，要连别的 scope 一起导就加 `allScopes: true` |
| `memory_import` | 从包导入：**按全文 sha256 判重、可反复跑**，`dryRun: true` 只演练；导入的向量用当前模型重算 |

> `memory_selftest` **不是常驻工具**：它是 Phase 0 的注册探针（注册 → 读回 → 立即注销，
> `probeToolRegistration`，`lib/index.js:192`），只在诊断路由的能力自检里跑，所以工具目录里看不到它。

### 自主录入（两条通路）

**通路一：跟随 agent 运行的后台捕获（原生，不需要 agent「记得去记」）**

插件挂 `session/event`（`user/message` / `assistant/message` / `turn/end`），把对话攒成转录；
在**回合结束**时如果「还没抽走的用户正文」达到阈值（默认 120 字）且过了冷却（默认 120 秒），
就在后台用 LLM 抽一次事实（默认 `focused`：只抽关系 / 偏好 / 经历 / 拍板决策）。

抽出来的记忆落到哪里，**按来源分**（2026-10-06 定的规则）：

| 来源 | 落点 | 说明 |
|---|---|---|
| **连入记忆系统的那个 agent 自己**的会话 | **免审直接入库**（三分类判 `uncertain` 的除外：它进待审区） | `capture.mode: 'direct'`（默认）。`source: 自主捕获`、`kind: auto`、`meta.capturedFrom` 记着会话与回合；被判 `uncertain` 的事实**不直存**，并成一个 `open` 待审批次（`capture.lastRun.batchId`）等人审 |
| 其他来源（子代理 / 被委派的会话，`header.origin==='subagent'`、有 `parentSession`、`delegationDepth>0`） | **待审区 → 由这个 agent 审阅** | 用同一套冲突判定（四关系 + 四条护栏）自动审：`supersede` 只改**最相似的那一条**、`duplicate` 跳过、其余入库；`review.agent: false` 时留给人审 |

三条不变量：**绝不阻塞回合**（监听器同步返回、抽取走后台）、**节流**（阈值 + 冷却）、**可关**（`capture.enabled: false`）。

**两道闸（2026-10-07 新增；同日升级为三分类）**：抽出来的事实要过两关才可能落库 ——
① **提示词**（`EXTRACT_PROMPT` / `EXTRACT_FOCUSED_PROMPT`）里写死了「不要记」清单与正反例对照：
会话/任务态（本次对话的安排、分工、约定、待办、进度汇报）、工具/协作态（teammate / subagent / 进程在做什么、
工具调用结果、待审区 / 变更单、刚改完待重启待验收）、助手自身的立场与自述、一次性当下状态（目前 / 正在 / 刚刚 / 这轮 / 暂定）；
> ⚠️ 2026-10-08 又补了一条更精确的：**不得从助手的话里反推本人的拍板** —— 转录里「助手：」开头的行只是上下文，
> 要记成「用户/本人拍板…」必须能从「用户：」行读到本人自己的话。真机漏过一次：助手在汇报里写的合并正文，
> 被抽取器当成「用户于…拍板」记进了库（同一件事因此出现了**第三份**）。另外 `ConversationBuffer.note()`
> 现在也过 `isHumanMessage()`：只有人说的话计入 `minChars`、只有人说的话以「用户：」进转录（见 `capture.minChars`）；
② **确定性三分类**（`src/host/transient.js` 的 `looksTransient()` → `durable` / `transient` / `uncertain`）：
提示词不是保证，所以抽出来的 fact 在**写库 / 入待审区之前**再逐条分类（`capture.dropTransient`，默认 `true`）：

- **`durable`（保留）**：命中**长期信号**一律保留，**即使同时出现技术词** —— `决定` / `采纳` / `拍板` / `统一` /
  `约定`（须有「用户 / 宝宝 / 小屿」这类人称主体、且不是 `约定：` 冒号清单）/ `偏好` / `习惯` / `要求` / `记住` /
  `基准` / `长期` / 日期锚点（`2026-10-07`、`08-12`）。**技术词（`变更单` / `待审区` / `验收` / `重启` / `panel` / `工具`）
  单独出现不再构成 transient**（旧二分类正是拿这些词误杀了「只出变更单、不直接改库」这类长期决定）；
- **`transient`（丢）**：纯**进度 / 协作 / 会话态** —— `teammate` / `subagent` / `子代理`、以「助手 / 我」**作句首主语**
  的立场与动作、`正在` / `刚刚` / `这轮` / `本次会话` / `接下来` / `待办` / `进度`、`跑通了 N 条`、`约好用…流程`、
  `约定：…`（冒号清单）。这类句子**没有长期事实主体**，**不受长期信号豁免**；
- **`uncertain`（拿不准）**：既不是上面的会话态句式、又没有明确长期锚点 → **不丢也不直存**，
  **并进待审区**等人审（直存路径会为它建一个待审批次，不自动落库）。

计数在 `memory_stats.capture`：`lastRun.droppedTransient` / `capture.droppedTransient`（判临时丢掉的）、
`lastRun.deferredToReview` / `capture.deferredToReview`（判拿不准、转待审的），`memory_stats.capture` 里。
手动 `memory_extract` 默认走同一道三分类（传 `excludeTransient: false` 可关；关掉 = 三分类全部保留）。
⚠️ 这道分类器是**启发式**：旧的「误杀长期决定」已按用户点名的 3 条真实例收窄（技术词不再单独构成 transient），
拿不准的一律走审阅而不再丢弃；判据与**剩余**已知边界见「已知限制」第 18 条与 `src/host/transient.js` 文件注释。

状态（最近几次捕获、跳过次数、错误）在 `memory_stats.capture` 与 `memory_stats.capture` 里。

（面板上没有手动录入了：事实直接交给 agent，或调工具）

| 动作 | 怎么走 | 结果 |
|---|---|---|
| **原文直存** | 面板「原文直存」/ 工具 `memory_remember` | 原文保真、秒级、**不过 LLM**，直接进库 |
| **交给 LLM 提取** | 面板「交给 LLM 提取」/ 工具 `memory_extract` | 模型拆成一条条事实 → **过一道确定性三分类**（默认开，`excludeTransient: false` 可关）→ 判 `transient` 的丢掉、`durable` 与 `uncertain` 落**待审区** → 由那个 agent 审阅（或人审）后入库 |

两者都在 `scope: config.scope` 下写入，密钥与出网范围与其它路径一致 —— **只有配置的 LLM 会看到这些文本**。

### 仓管（自带一条 LLM 通道：线上 / 局域网 / 本机，多档案可切换）

插件**自带**一条 LLM 通道（`keeper.*`），与宿主的 `ctx.llm` 完全无关：直连 **Ollama**（`POST /api/chat`）
或**任何 OpenAI 兼容端点**（`POST /chat/completions`，线上 DashScope / 局域网 vLLM / llama.cpp / LM Studio 都算）。
它扮演记忆系统的**仓管**，对已经录入的记忆做全库二次加工（上千条 × 每条一次调用，所以默认建议指向内网、不烧云钱）。

**通道是「档案制」的**：一个档案 = 一套端点 + 模型 + 参数，存在库里；面板上点一下就能切，**不用改补丁文件、不用重启**。

| 概念 | 存在哪 | 说明 |
|---|---|---|
| 档案 | 库里的 `settings.keeper.profiles`（JSON 数组） | 一组 `keeper` 字段：`provider` / `baseUrl` / `ollamaUrl` / `model` / `apiKeyRef` / 超时与各阈值 |
| 生效档案 | 库里的 `settings.keeper.active` | 档案名；**内置只读档案 `config`** 来自 profile 补丁，**永远排第一、不可删**，是兜底 |
| 合并规则 | — | 生效档案是 `config` → `keeper` = patch + `keeper.overrides`；是具名档案 → patch + **该档案自己的字段**（`overrides` 不参与合并） |

**首批种子**（只在 `keeper.profiles` 这个键**从没写过**时播一次；删光了不会再塞回来）：

| 种子档案 | `provider` | 端点 | 模型 | 密钥引用 | 开箱状态 |
|---|---|---|---|---|---|
| **线上** | `openai` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` | `DASHSCOPE_API_KEY` | ⚠️ **模型名是占位**，按你实际能用的模型改 |
| **局域网-ollama** | `ollama` | 留空待填（如 `http://<局域网 IP>:11434`） | 留空待填 | 不需要 | 如实报「未配置」，不拿本机默认 11434 乱连 |

播种是 `listKeeperProfiles()` 的副作用，所以**首次 `/state`、`memory_stats`、`action=profiles` 都会顺手播一次**；
`action=test {name}` 那条路径也会先播种（不然重启后第一件事测档案会假报「没有这个档案」）。

**`provider` 怎么选**：`openai` = 任何 OpenAI 兼容端点（**线上** DashScope / OpenAI，或**局域网**里的兼容端点）；
`ollama` = Ollama 原生 `/api/chat`（**本机**或**局域网内网 IP**）。改端点 / 模型：面板「仓管 → 档案」，
或工具 `memory_keeper {action:'save', …}` —— **保存只写库、不切换**；改完先 `test {name}` 试通，再 `activate {name}`。

**范式：出单（plan）→ 审阅（review）→ 落库（apply）**（2026-10-07 凌晨升级；旧的「跑一轮直接改库」已删除）

仓管**不再直接改记忆库**：一轮 `run` 只产出若干张**变更单**（写进新表 `keeper_plans`，v3 引入；当前 `SCHEMA_VERSION=5`），
每张单里是若干条 op（`split` / `replace` / `merge` / `drop`，带 `before` / `after` / `warnings`）。
**只有人（或 agent）审过、`reviewKeeperPlan()` 被调用，记忆正文才会变**；没审的单永远是 `open`。

> **统一修改语义（用户 2026-10-07 拍板）**：「修改记忆的做法是 **依照原记忆编写修改后的记忆** →
> **新旧记忆展示在待审区** → **过审后删除原记忆、录入新记忆**」。
> 所以修改类 op **只有 `replace`**（旧的 `rewrite` 一律按它解析 / 落库，**没有「原地改写同一条」这条路径**）：
> 单子里 `before` = 原记忆、`after` = 新正文，面板「仓管」页展开这张单就能看两者；过审时服务端
> `addMemory` 出**新 id** → 原条 `softDeleteMemory`（**软删 = 系统默认的「删除」**：整行与 history 都还在、可恢复）
> → 清原条向量 → 新条排队补向量，并把 `meta.replaces`（原 id）/ `meta.replacedAt` / `meta.model` 记在新条上。
> **`meta.model` 署的是"产出这张单的模型"**（存进 `keeper_plans.model`）—— 主仓管那一轮署它自己的模型、
> 副仓管接手署接手模型，**两条线各署各的**（用户 2026-10-08「主副仓管独立」）。老单没有这一列 → 署 `null`
> （不知道是谁产的，**不假装**）。之前读的是"主仓管那一轮的 job"，于是副仓管出的单会被盖成主仓管的模型名。
> 因为原条会被删掉，`after` 必须是**完整自足的新正文**（读的人拿不到原条上下文）。
> 手工入口：工具 `memory_keeper {action:'propose', id, text, reason?}` —— **只出单、不落库**，返回 `{ok, planId}`。
> 删除也有对称的手工入口 `memory_keeper {action:'propose-drop', id, reason?}` —— 同样**只出单、不落库**，
> 过审后该条**软删**（行仍在、可恢复），`action=revert` 能把它放回来（凭已应用变更单里的 `drop` op）。

| 动作 | 做什么 | 怎么触发 |
|---|---|---|
| **出单**（run） | 随机抽 `keeper.sampleSize`（20）个种子 → 每个种子用 embedding 语义召回 `keeper.perGroup`（5）个邻居组成一组 → 每组一次调用产出**一张变更单**（`maxGroups` 可限本次组数）。**记忆库一个字都不改** | 工具 `memory_keeper {action:'run', sample, perGroup, maxGroups}` / 面板仓管卡片上的「出变更单（随机抽样）」「抽样 + 去重合并」按钮（两个都只出单，打的是 `/keeper` 兼容别名）/ `POST /keeper-run` |
| **看单**（plans / plan） | `plans` 列出变更单（新的在前，带拍平的 `warnings`，`state` 可筛 open/approved/rejected/partial）；`plan {id}` 看单张全文 | 工具 `{action:'plans'\|'plan', id, state}` / 面板「**待办**」页 / `GET /keeper-plans`、`GET /keeper-plan` |
| **审阅落库**（review） | **唯一会改记忆库的入口**：`keep` 勾选要应用的 op 下标（省略 = 全部）；`edits` 就地手改正文（`split` → 字符串数组，`replace` / `merge` → 字符串，`drop` 忽略）；`reject:true` 整单驳回、一个字都不碰。落库动作：**`replace` = 删旧录新**（原条软删、可恢复 + 清原条向量；新条新 id、记 `meta.replaces`、排队补向量，`op.newId` 写回单子供面板显示）—— 旧 `rewrite` 也走这条；`split` 第 1 块写回原文 + 其余作为派生条入库（`meta.derivedFrom`）、`merge` 保留第一条（被并掉的 id 记进保留条的 `meta.merged`，回滚凭据）+ 其余软删、`drop` 软删；有跳过 → 单子记 `partial` | 工具 `{action:'review', id, keep, edits, reject}` / 面板「待办」→ 待确认那张单上「通过 / 驳回」 / `POST /keeper-plan-review` |
| **手工提出修改**（propose） | 对某一条已有记忆提出修改：`id` + `text`（修改后的**新正文**）+ 可选 `reason`。校验 id 存在且未删、`text` 非空且与原文不同 → 建一张单 op 的 `replace` 变更单（`state:open`，**不落库**），返回 `{ok, planId}`。**修改只能走这条路**：待审区看新旧对比、过审后才「删旧录新」 | 工具 `memory_keeper {action:'propose', id, text, reason}`（面板「待办」页展开这张单就能看 `before` / `after`） |
| **手工提出删除**（propose-drop） | 对某一条已有记忆提出**删除**：`id` + 可选 `reason`。校验 id 存在且未删 → 建一张单 op 的 `drop` 变更单（`state:open`，**不落库**），返回 `{ok, planId}`。**删除只能走这条路**（不许直删）：过审后该条**软删**（可恢复），`revert` 能放回来 | 工具 `memory_keeper {action:'propose-drop', id, reason}`（面板「待办」页展开这张单就能看要删的正文 `before`） |
| **回滚**（revert） | ① 删掉研磨产物；② 按 `history.prev_text` 恢复**历史遗留**的直改痕迹；③ 放回 `merge` **软删**的其余条（凭保留条上的 `meta.merged`）；④ **`replace` 的新记忆真删、原记忆放回来**（凭新条上的 `meta.replaces`；原条是软删所以可恢复，放回后重新排队补向量）；⑤ **放回 `drop` 软删的条**（`drop` 的目标行上没有 meta 痕迹，所以从**已应用变更单**（`approved` / `partial`）里的 `drop` op 取 `targets`，`propose-drop` 与仓管自己出的 drop op 共用这条路；统计在 `restoredDropped`）。⚠️ 它**不**把合并保留条 / 历史被改写条的正文回退（那些只有 `history.prev_text`，要手工恢复）—— 但 `replace` 的原记忆正文**没有被动过**，放回来就是原样 | 工具 `memory_keeper {action:'revert'}` / 面板「回滚仓管改动」/ `POST /keeper-revert` |
| **档案**（profiles / save / delete / activate） | 列档案（`config` 排第一）/ 新建或覆盖（**只写库、不切换**）/ 删档案（删掉的正好是**生效档案**时**自动回落 `config`**）/ 切换生效档案（**立刻生效、不用重启**） | 面板「仓管 → 档案」；工具 `memory_keeper {action:'profiles'\|'save'\|'delete'\|'activate', name, …}` |
| 状态 / 连通 | `action=status` 看配置、进度、待审单数（`openPlans`）与副仓管队列长度（`openHandoffs`）；`action=test`（可带 `name`：**只测那个档案、不改 active**）真打一次请求验连通性 | 面板「设置 → 仓管模型」的「测试」/ `GET /keeper`、`POST /keeper-test` |

> 这些单子在面板「**仓管**」页里读：默认是**按轮次分的处理流水**（每轮一行：几张单 · 通过 / 驳回），
> 点一行才展开改动前 / 改动后与机器提示；**只有「等你确认」的单子才出现「通过 / 驳回」按钮**。
> 服务端对已定案的单子**拒绝重复审阅**（`reviewKeeperPlan()` 判 `state !== 'open'` → 回
> `变更单已是 xxx，不能重复审阅`），所以流水里已定案的行天然是只读的。

> ⚠️ `provider=openai` 的档案**必须有可用密钥**（在面板「设置」里按该档案的 `apiKeyRef` 写入），
> 否则仓管如实报「取不到密钥」而不是发一个坏请求；密钥只进 DSH 凭据库，永不落进档案。

> 🔁 **超时不再白干：同一组自动重试一次**（2026-10-07 实测）。线上模型（`qwen3.8-flash`）吐 2000 token
> 的 JSON 实测约 **1/3 的组会超时**（`TimeoutError [23]`）—— 那一组进组的 tidy **照加**、却一行产出都没有，
> 采样机会白花。所以 `runKeeperRun()` **只在超时**时用**同一份请求**再打一次：重试是同一组，
> **不重复计 tidy、不重复建单**；第二次仍超时才记该组 `failed`，`tail` 写「组 N：失败（超时，已重试一次）」。
> 非超时错误（HTTP 4xx/5xx、响应格式错）**不重试**，错误原文直接进 `tail` / `lastError`。
> 默认 `keeper.timeoutMs` 也从 `120000` 提到 **`240000`**（具名档案可各自覆盖，见「配置」表）；
> `publicKeeper().retried` 如实记本轮重试了几次（**观测用**，面板不强求展示）。

> 🧯 **单组出错不再白干：跳过它、挂进「待接手记忆」、让接手模型接着做完**（2026-10-07，用户原话
> 「让仓管跳过这块记忆，并将这块待整理的记忆挂到『待接手记忆』，并让本地 LLM 模型接手继续整理」）。
> 四个失败口（非超时错误 / 超时重试仍失败 / 答了但解析不出操作 / 挂队列写失败）都走
> `handOffGroup()`：**跳过这一组** → 写一行 `keeper_handoffs`（**待接手记忆**，schema v5；同一组
> 反复失败**就地累加 `attempts`**、不插新行）→ 当场让**接手模型**重做那一组。
> **接手顺序**：① **本地 / 局域网仓管档案**（`configured` 且端点按 `isLocalEndpoint()` 判为
> 本机 / 内网 —— 只看地址**不看档案名**，名字是人随手起的）→ ② **宿主模型**（`ctx.llm`）。
> 两条都没有就如实写 `组 N：没有可接手的模型（原因） → 留在待接手记忆`；**标签永远写明是谁接的手**，
> 宿主模型不会被冒充成本地模型。**接手成功照样只出一张变更单**（`takenOver` 记数，`failed` 不算）、
> 接手也失败才计 `failed` 并**把接手失败的原因写回那一行**（面板照它显示「为什么还在这儿」）。
> 面板「**副仓管**」页里那一块给 `接手` / `清掉`（清掉是软状态 `dropped`，行还在）；`接手` 用的模型就是
> 那一页顶部选的**副仓管角色**（`settings.keeper.side`，选一次存库）；工具侧同样是
> `memory_keeper {action:'handoffs'|'takeover'|'drop-handoff'}`。**这一轮一个字都不改记忆正文**的口径不变。
>
> ⚠️ **隐私与成本（如实说）**：没有配本地档案时，那一组的记忆会发给**宿主模型**；不想这样就必须
> 自己配一个局域网 / 本机档案（或者失败后不管它 —— 结果就是它一直躺在待接手队列里，直到你清掉）。
> 每组失败会**多打一次模型**，本地模型慢的话一轮会更久。

**「事实保全」由代码给出证据，但「怎么改写」交给模型视情况决策**（需求原话是「无损研磨」；2026-10-07 最终语义，
用户原话：「**灵活一些 让LLM视情况决策 缩写、去冗余、优化语序 都是被允许的**」）：

1. **`replace` / `merge` 允许改写，唯一不变量是「事实要点不许丢」** —— 缩写、去冗余、优化语序、
   同义换词、把几句话理顺、合并、必要时改错别字**都放行**（这些不再被当成问题）；
   不许丢的是：人物 / 时间 / 决定 / 数值（数字、日期、版本号、端口）/ **引号里的原话** /
   emoji 与标签符号（🎞️🎥📍💬🔊 之类）。同时**不许新增**原文没有的事实、**不许把「可能 / 大概」写成断言** ——
   前一条（不许新增）现在有**代码证据**了（第 2 条末尾的 `addedTerms()`），后一条仍由**提示词 + 人审**负责；
2. **代码只给证据，不做「违规」定性**：`factCheck()` / `addedTerms()` / `selfContained()` 产出证据，
   `factWarnings()` 翻成人话写进 op 的 `warnings[]`：
   - `丢了 N 个数字：…`（**硬信号**：原文的数字 / 日期在改后文本里找不到了）；
   - `消失的片段：…`（**中性线索**：按**内容片段**比对 —— 引号原话 / emoji 标签 / 汉字串 / 拉丁词；
     **引号原话与 emoji 标签优先列在最前面**，片段过长会截断）；
   - `压缩到 X%`（**中性线索**：改后长度 ÷ 原文长度）；**只在压得极狠（< 40%）时才附一句
     「留意是否过度缩写」** —— 正常去冗余变短**不报警**；
   - `这块可能缺主语：…`（**新**：after 命中不了原文的任何锚点 —— 主语 / 对象 / 时间锚全丢，
     例如只剩「边界=…」。脱离上下文会被读成一条全局规则，**很危险**）；
   - `新增了原文没有的片段：…`（**新**：after 里出现了原文字典里没有的**连续新字** ——
     「允许重复，禁止发明」。重复原文里的主语词不算新增，纯去冗余 / 语序调整 / 同义换词也**不会**被误报）；
3. **`split`（拆细）跑「每块自足 + 不丢内容 + 不新增」三条证据**（用户 2026-10-07 发现的现象：
   拆出来的块会丢主语 —— 「第二块是指劳工边界，可它只说边界，这样会被理解为某个全局边界，**这很危险**，
   因此整理后的记忆块要完整」）：
   - **每块自足**：每块必须命中原文的锚点（专有名词 / 引号内术语 / 英文与数字标识 / 高频 2–4 字主题词），
     命中不了就报「这块可能缺主语」；**为此允许重复原文里的主语词**（重复不算冗余，缺主语才是问题）；
     提示词里也把这条放在**最显眼处**（配「边界=…」这种反例）；
   - **不丢内容**：各块合起来仍要覆盖原文（`丢了 N 个数字` / `消失的片段` 照旧）；
   - **不新增信息**：各块里出现原文字典里没有的新字就报「新增了原文没有的片段」。
   ⚠️ **旧承诺「`split` 逐字无损 / 子序列 ≥98%」已作废**：为自足而重复的主语词天然不是原文的子序列，
     再拿覆盖率兜底会把**想要的输出**丢掉。`coverageOf()` / `losslessSplit()` 在 `keeper.js` 里**保留** ——
     前者只是核对工具，后者只在「模型没给可用碎片 / 只给了一块」时**兜底**（记「兜底切分（模型…）」）；
4. 证据**只写进 `warnings[]`，不改判、不自动拒绝**：觉得模型改得不好，就在 `review` 里用 `edits` 手改，或整单 `reject`；
5. 判据在 `test/keeper.test.js`：同义换词（改成→改为）/ 改错别字 / 纯语序优化 → op 照出，只有「消失的片段」这类中性证据
   （**纯语序优化且要点齐全时零警告**）；丢数字 / 丢引号原话 / 丢 emoji → 警告且优先列出；
   只有「边界=…」这种缺主语的块 → 「这块可能缺主语」；模型自己造词 → 「新增了原文没有的片段」；
   极低压缩比 → 「留意是否过度缩写」，正常去冗余变短 → 没有它。三条自足证据**都不拦着出单**：
   缺主语 / 新增片段的 op 照样进单子，人自己看。

> ⚠️ 如实知道的边界（都不是 bug）：
> - **`addedTerms()` 只认「连续 ≥2 个原文里没有的新字」**（这样同义换词 / 语序调整不会天天狼来了；
>   反过来说，用原文里的字重新拼出来的新说法它抓不到），**「把不确定写成确定」也检测不了** ——
>   这两处仍靠提示词约束 + 人审，见上面第 1 条；
> - **`merge` 的压缩比拿「各条原文的并集」当分母**，所以多路合并天然显得压得很狠
>   （几条近似重复并成一条 → 25% 很常见），此时「留意是否过度缩写」只是提醒你回头看一眼；
> - 片段级比对**不逐字**，删掉一个虚词这种极小改动可能不出现在「消失的片段」里（有「压缩到 X%」兜着）。

> ⚠️ 落库前请先看一眼单子：`review` **会改正文、会软删**（`drop` / `merge` 的其余条；`replace` 是删旧录新），`split` 会产生派生条。
> 心里没底就先 `memory_backup`，或先只勾 `keep: [0]` 审一条看效果；
> `merge` / `replace` **软删**掉的条可以一键放回来（`action: 'revert'`：merge 凭保留条上的 `meta.merged`，
> replace 凭新条上的 `meta.replaces`，并把新条真删），历史遗留的直改痕迹也能用它清干净 ——
> 但**被改写的正文**（`merge` 的保留条、历史 `rewrite` 痕迹）它不回退，那条路只有 `history.prev_text`。
> **审过的单（`approved` / `rejected` / `partial`）不能再审第二次**。

### 两个行为计数器（读取指数 / 整理指数）与每周衰减

每条记忆有两个**行为计数器**（`memories.read_score` / `memories.tidy_score`，schema v4 起）：
记录它「被正常读过多少次」「被仓管整理过多少次」。它们只记行为，不改正文，也不参与检索排序。

**用户原话**：「为每条记忆附加两种参数：一个是被 agent 作为正常记忆读取后会增长一次的指数；
一个是被仓管作为待整理记忆读取后会增长一次的指数。整理指数会每周按全库指数高低差进行保持原比例
不变的小幅度下降以防数值膨胀。被整理后产生的新记忆初始会增长一次整理指数」。

| 计数器 | 什么时候 +1 | **不算**的情况 |
|---|---|---|
| **读取指数 `readScore`** | `memory_search` 命中的**每一条**；`memory_get` 取的**那一条** | 列表 / 面板浏览、`memory_list`、面板搜索（`/search` 直接调 `searchText`）、**仓管的分组召回与冲突分析**——它们共用 `searchText`，所以加分只放在**面向工具的 handler** 里，不在 `searchText` 里 |
| **整理指数 `tidyScore`** | 一条记忆**被抽进仓管的一组**（随机抽中的种子，或被 embedding 召回当邻居）——不管这组最后出不出单 | 同一轮里同一 id **只算一次**（跨组不会重复：进过组的 id 不会进第二组） |

仓管的 `split` 派生的碎片、`replace` 产出的新条是**新记忆**：整理指数**初始 = 1**（字面：初始 0 再 +1）。
`merge` 的保留条、`split` 的第 1 块都是**既有行**（它们的整理指数在「进组」时已经加过），不会重复加。

**每周防膨胀衰减**：默认每周（7 天）全库 **×0.98**（`score.weeklyDecay` 可改）。三条不变量：

1. **懒触发**：启动时（`apply()`）与每次计分操作前检查一次；距上次不足 7 天直接返回，零开销；
2. **按整周数连乘**：`factor ** weeks`；时间戳只推进 `weeks × 7d`（**不是 `now`**），不足一周的余数留到下次；
3. **比例严格不变**：全体同乘一个数 —— 谁高谁低、相差几倍，衰减前后完全一样，只有绝对值缩水。

**首次启用不会给历史数据打折**：第一次发现没有 `score.decayedAt` 时只写入当前时间，一分不乘。

看数：`memory_stats` 的 `scores`（`totalRead` / `totalTidy` / `avgRead` / `avgTidy` / `topRead` / `topTidy` /
`decayFactor` / `decayedAt` / `nextDecayAt`），或`memory_stats.scores`（含下次衰减时间与读取最高的几条）。
搜索结果的每一行也会带两个小 Tag。

> 性能取舍：`memory_search` 命中后**一条批量 `UPDATE ... SET read_score = read_score + 1 WHERE id IN (...)`**，
> 不是 N 次单条写；计分写在返回结果**之后**、失败只记日志，绝不影响本次检索的返回。
> 另外 v4 把 FTS 的 UPDATE 同步触发器收窄成 `AFTER UPDATE OF text`，所以写计分列**不会**触发 FTS 删+插。

    （工具 schema 里 `scope` 只声明成 string，所以「全部」用一个显式布尔表达，不靠 `null`）；
  - 模块侧（`MemoryService.exportMemory` / `exportPack`）：省略 = 默认 scope，**显式 `scope: null` = 全部**；
  - 坏值（`scope: ''`、数字…）**直接抛错**，不会被静默当成全导或空导。

## 读取侧注入（Layer 0 常驻索引 + Layer 1 按需召回）

> **为什么有这一节（2026-10-08，外部评审 + 用户拍板）**：之前插件只在系统提示里放了一段「用法说明」，
> **记忆内容一条都不注入** —— 于是"想起来才去查"成了唯一路径（本机实测：读取指数合计只有 6，
> 而主会话已经跑到 100 轮）。外部评审的诊断是：缺的不是更聪明的检索，而是**一层零智能、每轮都在的
> 常驻索引**（`memory.md` 之所以自然，正因为它零 LLM、每会话无条件加载、而且**只是索引不是正文**）。
> 用户拍板的口径：**静默索引做底，只在"要按一条旧决定行事、而当前说法可能冲突"时才明说一句**。

两层都是**派生视图**：只读库、一个字都不写回（与「原文即真相 + 改库唯一入口」零冲突）。

| 层 | 挂在哪 | 内容 | 稳定性 | 预算 |
|---|---|---|---|---|
| **Layer 0 常驻索引** | `systemPrompt.section`（order 2501） | 8 槽：`【约定】`/`【事实】` 两组，一行 ≤60 字，带 `[mem#xxxxxxxx]` 编号与「归属·日期」 | **话题段内逐字节冻结**（保前缀缓存） | 8 槽 |
| **Layer 1 按需召回** | `systemPrompt.context`（order 1000000，尾部动态区） | 6 槽：`【刚记下】`（刚记住 / 刚拍板的，最多 3）+ `【相关】`（按覆盖度打分） | 每轮可变 —— 放尾部，miss 的代价封顶在它自己身上 | 6 槽 |

> **落点（2026-10-08 读宿主实现 + 实测）**：`context` 注册的内容会被并进宿主自己的
> `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.` 快照
> （`joinContextSections()` 用 `\n\n` 把所有 context 段拼起来），而该快照挂在消息尾部 ——
> `order: 1000000` 确实落在动态尾部，静态前缀不受影响。`section` 一侧实测也是**稳定 scope**：
> 同一话题段内 `index.at` 不前进、`recall.at` 每步前进（Layer 0 只建一次，Layer 1 每步重算）。

选法（全确定性，**零 LLM、零 embedding 调用**）：
- **Layer 0**：先放「人写的 / 旧基线 / `meta.pin`」的条目（`kind=manual|note`、`source` 以
  `热区基线/USER.md`、`热区基线/MEMORY.md` 开头），再用「最近入库」补满；长度 <8 或 >200 字的进不了索引
  （长正文留给按需 `memory_get`）；`meta.excludeFromIndex=true` 可显式踢出。末尾永远写一句
  「索引只放了 N 条；库里共 M 条，其余按需检索」—— **不让模型把"没在索引里"读成"不存在"**
  （抄 Claude Code loader 的截断警告）。
- **Layer 1**：用**最近一条主会话用户消息**当查询（子代理 / 委派会话的消息不算），`pickTerms()` 取
  CJK bigram + ASCII 词，`store.searchBySubstringsSync()` 同步 LIKE 找候选，再按
  「覆盖度 = Σ 命中词 idf / Σ 查询词 idf」排序。**闸门**：至少命中 2 个词，或一个**够独特**的词
  （长度 ≥4 且只被 ≤3 个候选命中，如 `reviewKeeperPlan`）—— 只蹭到一个「喜欢」这类高频短词的直接丢。
- **查询词只取「人说的话」**（2026-10-08）：`user/message` 是**共用信封** —— 插件注入、工作区指令基线
  （`source.kind='agent-instructions'`）、compaction 摘要（`{kind:'plugin',plugin:'compact'}`）、工具回灌
  （`kind:'tool'`）全都走它，正文在 **`event.data`** 里而不是 `event` 上。判据 `isHumanMessage()`
  （`src/host/capture.js`）取宽：**只有明确标了别的来源才排除**，没标来源的按人来 —— 多注一条只是尾部多一行
  噪音（可见可查），少注一条是**功能静默失效**（本插件踩过，见 `REGRESSION.md`）。
- **召回只给喂过查询词的那个会话**：`context` 是全局注册，子代理 / 委派会话组装提示词时也会调到同一个回调，
  拿 `agent.session.header.id` 与当前 cursor 比对，不一致就返回空串（拿不到 id 时照常渲染，同样是不静默失效）。
  **真机探针验过**：起一个子代理让它如实报自己的提示词 —— `<memory_index` 在（Layer 0 是全局的）、
  `<memory_recall` **不在**。
- **查询词现场从会话日志取，不等事件**（2026-10-08 实测出来的时序坑）：宿主的
  `session/event user/message` 是在该步提示词**组装之后**才到插件手上的（实测组装 `09:33:46.772`、
  喂入 `09:33:46.878`）—— 只靠事件会永远**慢一步**：第 1 步没有查询词，而"没有工具调用的回合"只有一步，
  于是那个回合永远拿不到本轮召回（拿到的还是上一轮的问题，比空着更糟）。现在
  `lastHumanMessage(session)` 直接读会话日志（`agent.session.surface.nodes` + `eventAt(seq)`，宿主自己也是
  这么读的），**最多往回扫 400 条**；读不到就回落到事件游标。`recall.source` 会如实记账用了哪条路。
- **查询词短于 `minQueryChars`（默认 6 字）就整条不注**：真机实测用户那句「重启完成」注进来 4 行，
  其中「永远不能骗宝宝」「主完成 serve 配置」两条与问题毫不相干 —— 短消息摊出的 bigram 全是高频词，
  闸门挡不住。**宁可不注，也不注噪音**（热列表照旧，它与查询无关）。
- **热列表只画有正文的条目**：`memory_remember` 写入后、仓管单审过之后（最多 3 条）会进热列表。
  但 `merge` / `replace` 过审后原条是软删的、拿不到正文，只剩一个 `[mem#xxxxxxxx]` 编号 —— 对模型是
  零信息（2026-10-08 真机在自己提示词里看到过这种空行）。两侧都挡：注入侧跳过空正文，出单侧只把
  **还活着**的条记进热列表。
- **同一块里近似重复的行只留一条**（`dedupeFloor`，默认 0.92）：比的是**模型看到的那段正文**
  （不能比整行 —— `[mem#xxxxxxxx]` 标签自带 ~11 个 bigram，会把分母灌水，实测"只差一个句号"的两行
  整行 Jaccard 只有 0.90，用 0.92 会被整批漏掉）。⚠️ 它只抓**字面**重复；真库普查（1368 条）：
  **0 组完全同文、5 对 ≥0.92**，而实际看到的"同一决定写了两遍"是语义重复（0.2 量级）—— 那种只能靠
  库级合并（`memory_keeper` 的 `digest`），注入期藏掉是治标。
- **为什么是同步 LIKE 而不是向量检索**：`systemPrompt` 的 provider 是**同步函数**，不能 await embedding；
  而且每步打一次 embedding 会给每个 step 加延迟与费用。语义检索仍留在"想起来之后"的工具路径里。
- **话题段冻结**：段内至少 `minSegmentTurns` 轮、消息 ≥6 字，且 bigram 衔接度（Jaccard）低于
  `cohesionFloor` 才算换话题；**换段才重建索引**（防"顺口一问"把上下文裁了，也防频繁改动把前缀缓存
  打散 —— 官方文档明写前缀一变会**全额 miss**、要等公共前缀落盘后第三次才重新命中）。
- **日期用内容日期**，不用入库时间：本机 1362 条的 `created_at` 全落在一次批量导入的两天里，
  mtime 当新鲜度是废的（外部评审的"按 mtime 排序"因此在本库不成立）。

**缓存红线（实测，不是估计）**：注入上线前用 `tools/cache-report.mjs` 扫本机会话投影 ——
最近 8 个会话 **命中率 99.09%**（命中 1040.05M / 未命中 9.51M）。注入上线后同一脚本复测：
**99.11%**（未命中 9.71M / 命中 1078.47M；主会话 `a6ce659d` 101 轮 99.1%）—— **没掉**。
这个数**不该掉出 95%**；机制上掉了就说明有动态内容挪到静态前缀前面去了。

**查"到底注进去没有"**：`memory_stats.recall` 一格给全 —— `section` / `context` 的注册状态、
`feed`（喂入台账：`fed` / `notHuman` / `foreign` / `disabled` / `noEngine` / `lastAt` / `lastChars` / `errors[]`）、
`engine`（`cursor` 查询词、`index.ids` 这一轮索引的 8 条、`recall.ids` 这一轮召回命中、`bytes`、话题段版本、
`recall.source`（`live` 现场取 / `cursor` 回落事件游标）、`recall.skip`（`short-query` / `no-match`）、
`recall.deduped`、`errors`）。
"注入块是空的"能一眼分成**查询词太短 / 没命中 / 别的会话 / 引擎没建起来 / 关了 / 出错**，不用猜。


**怎么关**：配置里 `recall.enabled = false`，两层立刻都返回空串 —— 注入是加分项，不是必需项。

## 配置

### 嵌入配置：三档来源，可随时切换

「线上 / 局域网 / 本地模型」都支持，**改配置不用改补丁文件、也不用重启**：

| 来源 | 存在哪 | 怎么改 |
|---|---|---|
| **档案**（推荐） | 库里的 `settings.embedding.profiles` + `settings.embedding.active` | 面板「设置 → 向量模型」：点档案名就地展开，填 `provider` / `baseUrl` / `model` / `dimensions` / `apiKeyRef`（Ollama 填 `ollamaUrl`，离线填 `localDims`）→ 保存 → **`测`** → 点圆点切生效（密钥在同一个编辑体里写） |
| **补丁配置** | profile 的 `cordis.patch.yml` 里的 `config.embedding`（**没写就是内置默认值**） | 改文件后热生效（Loader 重放 patch 层）。它是**兜底**：名字固定 `config`，宿主不许改也不许删；面板上**只在它生效时**出现一行（显示成「补丁配置」）—— 平时请用「档案」 |
| 环境变量 | `process.env[apiKeyRef]` | 密钥解析的第二顺位，只用于本地临时验证 |

三种 `provider` 覆盖三类部署：

| provider | 打哪个端点 | 适合 |
|---|---|---|
| `openai` | `POST {baseUrl}/embeddings`（Bearer 认证） | **线上**（DashScope / OpenAI / 任何 OpenAI 兼容网关）或**局域网**里的兼容端点 |
| `ollama` | `POST {ollamaUrl}/api/embed` | 本机或局域网的 Ollama |
| `local-hash` | 不联网 | 离线确定性兜底（维度 = `localDims`，只适合冒烟/测试，不具语义能力） |

**切换不会重算、也不会丢向量**：每个档案算出一个空间键 `provider:model:dims`，向量按它分组保留；
切到新档案 → `memory_stats` 显示「缺 N 条」→ `memory_embedding {action:'activate', autoFill:true}`（**只算缺的那些**）；
切回旧档案 → 只补「离开期间新增的」那几条，老的直接复用。详见 `DESIGN.md` §C.1 / §E.1。

### 补丁文件里的键

写在上面那个 patch 块的 `config:` 里（`normalizeConfig` 会深合并默认值并逐项校验，非法值直接抛错）：

| 键 | 默认 | 说明 |
|---|---|---|
| `dataDir` | `null` → `$DSH_HOME/dsh-memory` | 库文件所在目录，会自动创建 |
| `scope` | `'default'` | **写入**用的作用域（`memory_remember` 与面板写入）；**检索默认不过滤 scope** —— `memory_search` 与面板搜索都是全局视图 |
| `embedding.provider` | `'openai'` | `openai` / `ollama` / `local-hash`（离线确定性兜底） |
| `embedding.baseUrl` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | OpenAI 兼容端点（线上或局域网都写这里） |
| `embedding.model` | `qwen3.7-text-embedding` | 嵌入模型名 |
| `embedding.dimensions` | `1024` | **每批返回的向量长度必须等于它，不等就抛错**（错误信息含期望/实际维度与模型名） |
| `embedding.apiKeyRef` | `DASHSCOPE_API_KEY` | **只放引用名**，密钥本体在 DSH 凭据库；每个档案可以有各自的引用名 |
| `embedding.batchSize` / `timeoutMs` / `ollamaUrl` / `localDims` | `16` / `60000` / `http://127.0.0.1:11434` / `1024` | 批大小、超时、Ollama 地址、local-hash 维度 |
| `llm.provider` / `llm.model` | `null` / `null` | 留空即用宿主当前配置的模型 |
| `llm.extractMaxTokens` | `2000` | 抽取的 token 预算；**别压太小**，推理模型的思考会先把预算吃光 |
| `search.*` | `defaultLimit 8`、`maxLimit 100`、`keywordWeight 1`、`vectorWeight 1`、`rrfK 60` | 检索上限与 RRF 融合参数 |
| `capture.enabled` | `true` | **跟随 agent 运行的后台捕获**总开关。关掉后一条都不抽（也不花 LLM 调用） |
| `capture.mode` | `'direct'` | 只影响「连入的 agent 自己」的会话：`direct` = 抽出来**免审直接入库**；`pending` = 先落待审区。其他来源一律走待审 |
| `capture.focused` | `true` | 只抽「与人的关系 / 偏好 / 经历 / 拍板决策」，排除端口/路径这类技术细节 |
| `capture.minChars` | `120` | 还没抽走的**用户正文**累计到这个字数才触发（助手的话只作上下文、不计入）。⚠️ **「用户正文」只算人说的话**（`isHumanMessage()`，2026-10-08 补上）：`user/message` 是共用信封 —— 插件注入 / 工作区指令基线 / **compaction 摘要**都走它，以前不看 `source`，于是这些派生文本既灌满了这个阈值、又以「用户：…」的身份进了转录，抽取器把派生文本当成了用户亲口说的（真机：同一条拍板被捕获两遍、措辞都是派生文本的措辞） |
| `capture.maxChars` | `4000` | 单次转录上限；超出丢最旧的，保住最近上下文 |
| `capture.cooldownMs` | `120000` | 两次捕获的最小间隔（毫秒），防止每回合都花一次 LLM 调用 |
| `capture.dropTransient` | `true` | **第二道闸（三分类）**：`src/host/transient.js` 在写库 / 入待审区之前把事实判成 `durable`（保留）/ `transient`（会话·工具·进度态 → 丢）/ `uncertain`（拿不准 → 并进待审区，**不丢**）。技术词（`变更单` / `待审区` / `重启` / `panel`）单独出现**不再**构成 transient；命中 `决定 / 采纳 / 拍板 / 统一 / 约定 / 偏好 / 习惯 / 要求 / 基准 / 长期 / 日期` 这类长期信号的一律保留。`false` = 三分类全部保留（只靠提示词）。计数：`memory_stats.capture.droppedTransient`（丢）/ `deferredToReview`（转待审） |
| `review.agent` | `true` | 待审批次由**这个 agent** 自动审（冲突判定 + 四条护栏）；`false` = 留在面板等人审 |
| `review.topK` | `3` | 自动审阅时每条事实取多少条相似记忆当候选 |
| `score.weeklyDecay` | `0.98` | **两个行为计数器的每周衰减系数**（必须严格在 `(0,1)` 开区间内）：每周全库同乘一次，比例不变、绝对值缩水 2%；距上次 ≥7 整天才真正乘，按整周数连乘。`1` = 不衰减（数值会无限膨胀）、`0` = 一次归零，都不合法 |
| `recall.enabled` | `true` | **读取侧注入总开关**：`false` 时两层（常驻索引 + 按需召回）都返回空串、一个字都不进提示词 |
| `recall.indexSlots` / `indexPinnedCap` | `8` / `4` | 常驻索引几个槽 / 其中「人写的·旧基线·`meta.pin`」最多占几个（`indexPinnedCap ≤ indexSlots`） |
| `recall.recallSlots` / `charLimit` | `6` / `60` | 按需召回几个槽 / 每条卡片渲染多少字（两层共用） |
| `recall.minSegmentTurns` / `cohesionFloor` | `3` / `0.08` | 话题段判定：段内至少几轮 + bigram 衔接度（Jaccard）低于多少算换话题（换段才重建索引） |
| `recall.candidateLimit` / `terms` | `400` / `14` | 一次同步 LIKE 最多取多少候选 / 一条消息最多挑几个查询词 |
| `recall.minQueryChars` | `6` | 查询词短于这个字数就**整条不注**（只有热列表照旧）。真机实测：「重启完成」4 字注进来 4 行，其中两条与问题毫不相干 —— 短消息摊出的 bigram 全是「完成」「重启」这类高频词，闸门挡不住，只能整条不注 |
| `recall.dedupeFloor` | `0.92` | 同一块里两行正文的 bigram Jaccard ≥ 此值就丢掉后者（同一件事的两个版本会并排出现）。`0` = 关。行数可能因此少于 `recallSlots`（**少注优先于补位**）。⚠️ 它只抓**字面**近乎重复：真库实测 1368 条里 0 组完全同文、5 对 ≥0.92；而实际看到的"同一决定写了两遍"是**语义**重复（Jaccard 只有 0.2 量级），文本阈值够不着 —— 那种要靠库级合并（`memory_keeper` 的 `digest`） |
| `keeper.provider` | `'ollama'` | 仓管 LLM 的端点类型：`ollama`（`/api/chat`）或 `openai`（`/chat/completions`，任何兼容端点） |
| `keeper.ollamaUrl` | `null` | `provider=ollama` 时的地址。**局域网写内网 IP**（如 `http://<局域网 IP>:11434`）；`null` = 未配置 |
| `keeper.baseUrl` | `null` | `provider=openai` 时的兼容端点（如 `http://<局域网 IP>:8000/v1`） |
| `keeper.model` | `null` | 仓管用的模型名（如 `qwen3:8b`）。`null` = 未配置，仓管会如实报「未配置模型」 |
| `keeper.apiKeyRef` | `null` | `provider=openai` 时密钥的**引用名**（走 DSH 凭据库，与嵌入密钥同一套；Ollama 不需要） |
| `keeper.timeoutMs` / `maxTokens` / `temperature` | `240000` / `2000` / `0` | 单次调用超时、token 预算、温度（研磨要稳定，默认 0）。**240s 是 2026-10-07 从 120s 提上来的**：线上模型吐 2000 token 的 JSON 实测可能过 2 分钟；同组超时还会自动重试一次（见「仓管」节） |
| `keeper.groupTimeoutMs` | `0` | **一组的硬墙钟安全网**（毫秒；`0` = 自动 = `keeper.timeoutMs × 2`）。为什么需要它：`timeoutMs` 只管**单次请求**，而一组最坏会打两次（超时重试一次）。**为什么默认 2 倍而不是更小**：2026-10-08 真机实测，正常的一组（5 条记忆、2000 token JSON）跑了 **231 秒**才成功 —— 设 90 秒会把正常成果直接杀掉。⚠️ **到点后不自动接手**（2026-10-08 补）：真机上声明 480s、一组实际跑到 **602s** —— 因为"接手那一次"是在预算耗尽之后才开跑的，仅靠 `timeoutMs` 收不住它。现在到点就挂副审阅区**等人接手**（`job.tail` 写明「整组预算已用完 → 不自动接手」）；没到点的失败照旧当场接手。**留下的那一条会放回 `open`**（面板看得见），不会卡在认领态 |
| `keeper.minChars` | `240` | **研磨**的「大段」阈值（字数） |
| `keeper.digestMinChars` | `120` | ⚠️ **已作废**（新范式只出变更单，"消化"那一遍早没了）：配置里还认这个键（老档案读得动），但**逻辑一次都不用**，2026-10-07 起也从工具 schema 与 `keeperStatus()` 里摘掉了 |
| `keeper.splitChars` | `400` | 单块目标上限（也用于确定性兜底切分） |
| `keeper.dedupeThreshold` | `0.86` | ⚠️ **已作废**（同上：没人读）。留着只为老档案不报错 |
| `diagnostics` | 未设（即关） | `true` 才开启 `/dsh-memory-selftest/*` 开发期诊断路由，**默认关**（见「已知限制」） |

> 上表 `keeper.*` 是**内置 `config` 档案**的字段（来自 patch，永远兜底）。**具名档案**（线上 / 局域网-ollama …）
> 在面板「仓管 → 档案」或 `memory_keeper {action:'save'|'activate'}` 里管，存在 DB 的 `keeper.profiles` / `keeper.active`；
> 生效档案不是 `config` 时，patch 里的值只作缺省打底，`keeper.overrides`（面板「仓管 → 配置」那几个框）**不参与合并** —— 要改参数就改**当前生效的那个档案**。

### 密钥

- 解析顺序：`ctx.credentials.resolve(apiKeyRef)` → `process.env[apiKeyRef]`；
- 写入：面板「设置 → 展开某个档案 → 写入密钥」调 `ctx.credentials.set`，**只进 DSH 凭据库**；
  写入时按**所选档案的 `apiKeyRef`** 落库，所以「线上一个 key、局域网另一个 key」互不干扰；
- **密钥永不落进本插件生成的任何文件**（不写 config、不写档案、不写导出包、不写日志）。

## 已知限制（诚实版）

1. **中文关键词查询建议 ≥3 字**。FTS5 用的是 `trigram` 分词器，2 字词（宝宝 / 咖啡 / 偏好）和 1 字词
   它**指数级命不中**，所以代码里对 `<3 字` 走的是 `LIKE '%…%'` 全表兜底 —— 能查到，
   但那是全表扫描、也不是分词，别指望它做复杂的短词组合。实测 5000 行 LIKE 0.1 ms，够用但不是索引。
2. **向量检索是暴力余弦**，没有 ANN 索引。实测 4000×2560 维 22.6 ms，在**万级条数**内完全够；
   到了十万级就得换方案（现在没有）。
3. **LLM 抽取/冲突判定依赖宿主已配置的模型**，插件不自己管模型。且适配器**只取 `text-delta`、
   丢弃 `reasoning-delta`**：推理模型的思考过程一旦被拼进去，JSON 解析必然失败、表面上却「LLM 正常返回了」。
   随之而来的限制是：`maxTokens` 太小（比如 32）时可能**一个 `text-delta` 都没有**，抽取会得到 0 条。
4. **`diagnostics: true` 会开一条无鉴权的本机诊断路由** `/dsh-memory-selftest/*`
   （不走 `/api`，因此没有 Cookie 栅栏，只监听回环）。它上面有 `/import`（读任意文件）、
   `/credential`（写凭据）、`/clean`（改数据）、`/search`（吐记忆正文）——**本机任何进程都能调**。
   **默认关，不要长期开着**；排查完就把这一行删掉。
5. **面板不再有手动抽取**：抽取从工具侧触发（`memory_extract`）。
6. **`memory_forget` 是软删**：默认查询看不到它，但行还在库里（`includeDeleted` 能看到）；
   要彻底删得走硬删接口。软删的正文仍占用库空间。
7. **导出默认只导一个 scope**（`manifest.scope` 会如实记录），别的 scope 的记忆不会被写进包。
   要全都导：工具加 `allScopes: true`（或模块层 `scope: null`）。这条以前是「工具做不到」——
   已修：`exportMemory` 不再用 `scope ?? config.scope` 把显式 null 吃掉，判据见 `test/export-scope.test.js`。
8. **导出包不含向量**（这是设计，不是缺陷）：导入后必须重建索引，否则那些记忆只有关键词路能命中。
9. **每个向量空间各存一套，会线性占空间**：1024 维 × float32 ≈ 4 KB/条，1087 条 ≈ 4.4 MB/空间。
   不用的空间可以删 —— 模块层 `store.deleteVectorsOfSpace(key)`，或直接
   `DELETE FROM vectors WHERE space = '<key>'`。v1→v2 升级留底的 `vectors_v1` 表也占一份，
   确认新库没问题后 `DROP TABLE vectors_v1` 即可回收（**库是派生物，删了最多重算**）。
10. **切换档案后要补齐才恢复语义检索**：`memory_stats` 会显示「缺 N 条」。补齐是真调嵌入接口，
    按条数 × 批次耗时算（1087 条量级约 2–4 分钟）。补齐期间配置又切走了 → 任务会自己停下并报错，
    不会把向量写错空间。
11. **备份会占空间**：一份 ≈ 库本体（含向量）+ 文本包；默认只留最近 5 份（`memory_backup` 的 `keep` 可调）。
    快照是标准 SQLite 文件，可以直接用任何 SQLite 工具打开。
12. **自主捕获会把对话正文发给配置的 LLM**（与 `memory_extract` 同一条路径）：数据仍只落在本机，
    但**抽取这一步出网** —— provider 是 `openai` 类就走云 API，`ollama` 就是局域网。
    不想让它出网：`capture.enabled: false`（或把 `llm`/`embedding` 都指到局域网模型）。
    另外它**会花 LLM 调用**：每达到一次阈值（默认 120 字 + 120 秒冷却）一次。
13. **自主捕获是「尽力而为」**：只挂进程内事件、失败只记状态不重试；缓冲上限 32 个会话（超了丢最老的）、
    单次转录上限 `capture.maxChars`。**它可能漏抽**（阈值不够、冷却中、LLM 不可用），
    所以「重要的东西」还是建议明确说一句「记住这个」。
14. **仓管出单阶段不动数据，落库才是「会动数据」的那一步**：`run` 只往 `keeper_plans` 写变更单，
    记忆正文 / meta / 向量一个都不碰；只有你（或 agent）在「仓管」页审阅通过，才会**删旧录新**
    （`replace`：新条新 id、原条**软删**=行仍在可恢复，原文也留在 `history` 里）、`split` 拆出派生条、
    `merge` / `drop` **软删**（可恢复）。手工改一条记忆也走同一条路：`memory_keeper {action:'propose'}` 只出单，
    审过才生效（**没有直接 `updateMemoryText` 修改的入口**）。
    `split` 拆出的每一块都跑「每块自足 / 不丢内容 / 不新增」三条证据（缺主语、模型自己加的片段都会在单子上报出来；
    **旧的「split 逐字无损」承诺已作废**，见上文仓管节第 3 条）；`replace` / `merge` 保证的是**事实要点不丢**。
    不想留痕就跑 `action: 'revert'`：它会放回 `merge` 软删的其余条（凭 `meta.merged`）、
    **把 `replace` 的新记忆真删并把原记忆放回来**（凭 `meta.replaces`），并清掉**历史遗留**的直改痕迹；
    合并保留条 / 历史被改写条的正文它不回退（只有 `history.prev_text`）。跑之前建议先 `memory_backup`。
15. **仓管慢是正常的**：一组（种子 + 语义召回的邻居）一次 LLM 调用，1087 条在局域网小模型上通常是
    **几十分钟到几小时**量级（取决于模型与 `sample` / `perGroup` / `splitChars`）。它是后台任务、不阻塞对话，
    但**进程重启会中断**（进度不续跑）—— 不过 `run` 本来就不写记忆库，重启后重跑只是重新出单：
    已经出好的单还在 `keeper_plans` 里，不重复落库。
16. **仓管档案改完立刻生效**（这是设计，不是缺陷）：不用改 patch、不用重启。反过来说，patch 里的 `keeper.*`
    只是**内置 `config` 档案**的兜底值 —— 生效档案切到具名档案后，`keeper.overrides`（面板「仓管 → 配置」那几个框）
    **不再参与合并**，对着它改参数是白改；要改就改**当前生效的那个档案**。
17. **检索会给命中条目写一次计分**：`memory_search` 每次命中都会批量 `UPDATE read_score`（一次 SQL，
    8 条量级实测 +1 ms 内；见 `REGRESSION.md` 的实测与取舍）。所以它是**读操作里唯一的写**：
    库是 WAL，读写互不阻塞；写失败只记日志、不影响检索返回。`memory_list` / 面板浏览**不写**。
    两个计数器的绝对值只增不减（每周统一乘系数），**不参与排序**，也不会因为分数低就被隐藏/删除。
18. **事实分类器是启发式的：误杀已收窄，拿不准的一律走审阅**（`capture.dropTransient`，默认开）。
    2026-10-07 由二分类升级为**三分类** `durable` / `transient` / `uncertain`（`src/host/transient.js`），
    最直接的动因是修掉**已确认的 3 条误杀**（用户点名的真实记忆，旧二分类会把它们静默丢掉）：
    - 「用户采纳了助手建议的四条语义：…只出变更单、不直接改库」（旧：命中 `变更单` → 丢）→ 现在 `durable`（`采纳`）；
    - 「用户和助手约定仓管的所有改动先进入独立待审区…」（旧：命中 `待审区` → 丢）→ 现在 `durable`（`约定` + 人称主体）；
    - 「用户决定记忆抽取暂定由自己手动启动」（旧：命中 `暂定` → 丢）→ 现在 `durable`（`决定`）。
    **修法**：技术词（`变更单` / `待审区` / `验收` / `重启` / `panel` / `工具`）单独出现**不再构成 transient**；
    命中长期信号的一律保留；既不是会话态句式、又没有长期锚点的一律 `uncertain` → **并进待审区，不丢**。
    它仍按**关键词 + 句式**判、不看上下文、没有语义理解，剩余已知边界如实列在这里：
    - **会漏**（会话态落进 `uncertain`，只是多一道人眼，不会丢）：句子里一个判据词都没有的会话态 ——
      真实库例「用户与助手历经多轮协作，最终拿到 201/201 测试通过」「助手安抚用户不必担心，说明记忆数据完好」
      「助手有一套自己写在文档里的安全流程：动数据前先备份」；
    - **仍可能误杀**（`transient`，会丢）：`约定：`（冒号清单）一律按会话步骤处理 —— 真写成冒号清单的
      **长期**约定若句子里没有任何长期锚点会被丢掉（如「用户和助手约定：先改代码再重启」）；
      以及以「助手 / 我」**作句首主语**且后接动词的句子（把「助手」当作某个人名/称呼的罕见写法会被误杀）；
    - **`uncertain` 的代价**：它**不自动**进库，直存路径会为它建一个 `open` 待审批次（`capture.lastRun.batchId`），
      等人审 / 再由 `review.agent` 处理 —— 所以 `deferredToReview` 一直涨时，待审区里会堆东西，需要有人看；
    - 不想要这道闸就设 `capture.dropTransient: false`（**三分类全部保留**，等价于不过闸）；
      手动抽取同理传 `excludeTransient: false`。

## 故障排查

| 现象 | 先看什么 | 常见根因 |

| **仓管连不上 / 一直失败** | 面板「仓管 → 测试连接」的 `error` 原文 | ① `keeper.ollamaUrl` 写成了本机却不在本机跑；② 局域网地址不通（先 `curl http://<ip>:11434/api/tags`）；③ `keeper.model` 名字不存在（Ollama 报 `model not found`）；④ **单组超时**（`TimeoutError [23]`）—— 线上模型吐 2000 token 的 JSON 可能过 2 分钟；已内置**同组超时自动重试一次**、默认 `keeper.timeoutMs` 也提到 `240000`（2026-10-07），仍不够就改**当前生效档案**的 `timeoutMs`（具名档案的字段盖过 patch） |
